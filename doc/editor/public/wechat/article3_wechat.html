2 核心流程：工具调用的四步闭环

当用户问"查销售数据"时，背后发生了什么？我们用时序图拆解：

🎯 步骤一：意图识别

模型判断用户需要查数据，而非闲聊。这取决于系统提示词中对 Agent 角色的定义。

🔍 步骤二：工具选择

模型从可用工具列表中选择 query_sales_by_product。工具描述越清晰，选择越精准。

📝 步骤三：参数提取

模型从用户话语中提取参数 product_name = "AI助手专业版"，即使名称有空格差异也能匹配。

📋 步骤四：执行反馈

Server 执行查询并将结构化结果返回给模型，模型据此生成最终的自然语言回复。

3 工具定义：模型理解能力的关键

MCP Server 通过装饰器暴露工具。本项目定义了两个工具：

工具名称 功能 参数
list_products 查询数据库中所有已有的产品名称列表 无
query_sales_by_product 查询指定产品的销售记录汇总（支持模糊匹配） product_name（字符串）

工具定义的核心三要素

🏷️ 装饰器标记

使用 @mcp.tool() 装饰器将普通函数注册为 MCP 工具，Server 启动后自动暴露该接口。

📝 文档描述

Docstring 是模型理解工具用途的唯一依据。描述包含适用场景、参数说明和返回值格式，越清晰调用越精准。

📐 类型提示

参数类型标注（如 product_name: str）帮助模型正确生成参数，减少类型错误。

💡 模糊匹配：当用户输入"AI助手专业版"但数据库存储为"AI 助手专业版"时，Server 会先精确匹配，失败后自动去除空格做模糊匹配，大大提升查询容错率。

4 项目结构：4 个文件搞定一切

agent.py
Agent 客户端核心。包含双模型后端（通义千问 / 智谱 GLM）、MCP 连接管理、工具调用循环。启动后交互式选择模型，支持上下键导航。
server.py
MCP 服务端。定义 list_products 和 query_sales_by_product 两个工具，连接 SQLite 数据库执行查询。
init_db.py
数据库初始化脚本。创建 sales_records 表并插入测试数据，只需运行一次。
.env
API Key 配置文件。存放 DASHSCOPE_API_KEY（通义千问）和 BIGMODEL_API_KEY（智谱 GLM），不提交到 Git。

    8 进阶特性：多步工具调用

    Agent 不限于单次工具调用，它支持链式推理 —— 模型可以根据第一次工具的结果，决定是否继续调用更多工具。

    为什么需要多步调用？ 想象用户问"对比两个产品的销售情况"。Agent 可以先调用 list_products 获取产品列表，再分别调用 query_sales_by_product 查询每个产品的数据，最后综合分析 —— 一切自动完成，用户只需一句话。

    9 双模型策略：一套架构，灵活切换

    10 调试指南

    🔍 模型不调用工具

    可能原因 解决方案
    工具描述不清晰优化 Docstring，增加适用场景说明
    参数类型不明确检查函数签名的 Type Hints
    系统提示词缺失在 Agent 中配置角色和可用工具说明

    🔍 模糊匹配不生效

    可能原因 解决方案
    差异不仅是空格在 Server 端扩展模糊匹配策略（如拼音、别名映射）
    产品名完全不同建议先调用 list_products 获取准确名称

    🔍 中文输入光标错位

    可能原因 解决方案
    使用了 Python 内置 input()已替换为 prompt_toolkit，完美支持中文光标定位

    11 安全红线：生产环境必读 ⚠️

    演示代码为教学简化，生产环境请务必遵守：

    ✅ 必须做 ❌ 绝对禁止
    数据库账号只读权限 暴露 DELETE / UPDATE 工具
    参数化查询防 SQL 注入 拼接字符串执行 SQL
    敏感配置走环境变量 硬编码密码 / 密钥
    记录工具调用审计日志 无日志裸奔上线
    破坏性操作需人工确认 自动执行高危命令
    ⚠️ 一句话原则：假设模型会被恶意诱导，每一层都要做校验。
